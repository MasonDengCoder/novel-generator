# 设计亮点：写作流水线与写验分离

> 本文档记录设计语义，不含命令语法。命令契约以 `contracts/cli/commands.md` 为唯一事实来源（SSOT）；实现状态以 `repository/dev-progress.md` 为准。涉及未实现实体标注"规划态"。
>
> 抽离来源：`docs/项目整体架构.md` §10 标准章节写作流水线、§9.3 写验分离与裁决存在性门禁；`docs/Spec架构设计.md` §5 章节写作数据流、§4 LLM 切入点。

---

## 1. 核心原则：写验分离

写作与验证必须分离：

- **写作代理只负责写正文**，不背负状态一致性、权限判断、主线落地自评。
- **主线落地、越界、整体一致性等判断，必须由独立验证流程完成**。
- **写作者不得自评**——主线落地裁决由独立 verifier 写入，CLI 状态推进只读裁决位。

凡是"忘了就会崩"的内容，都必须落到 CLI 管理的确定性数据中；凡是可以确定性检查的规则，都应由 CLI 执行，不依赖 LLM 自觉遵守。

---

## 2. 标准章节写作流水线

逐章运行必须拆成多步，而非"拿 context 直接写"：

```text
 0. 章节预检
 1. 获取章节关联信息
 2. 编译 Chapter Context Packet
 3. 生成章节目标任务列表
 4. 校验并固化任务列表
 5. 撰写章节正文
 6. 通过 CLI 写入正文并计算 hash / 字数
 7. 确定性检测：规则、撞极、收束、格式
 8. 独立验收：按任务列表验证
 9. 失败则进入修复循环
10. 提取残余、四相日志、涌现候选
11. 更新事件、支线、伏笔、角色、承诺等关联状态
12. 章节进入 review
13. 章节进入 approved
14. 归档章节
15. 更新创作进度，判断是否触发卷末大轮回
```

关键原则：

- 写前阶段只准备和确认，不直接生成正文。
- 写作代理不得直接修改世界状态。
- 写后先执行确定性检测，再执行独立语义验收。
- 验收失败时只修复 verifier 指出的偏移，不扩大章节目标。
- 正文通过基本验收前，不应更新事件、角色、伏笔、承诺等结构化世界状态。
- 状态推进和归档必须最后执行。

> 各步骤通过对应 CLI 命令完成（见 `contracts/cli/commands.md`）；状态推进门禁见 `contracts/cli/state-machine.md`。

## 3. LLM 角色（Spec 功能模块）

LLM 不直接接触 SQLite 或正文存储，与世界状态的交互只发生在受控切入点：

| 角色 | 职责 | 切入点 |
|---|---|---|
| **writer** | 消费 writer view + 固化任务列表，生成正文草稿及残余/四相/涌现候选。 | 写前读取（chapter context writer view）、正文写入（chapter update）。 |
| **task planner** | 消费 writer view，生成 Chapter Task List。 | 写前读取。 |
| **context auditor** | 读取 context audit 与 overflow，判断省略风险。 | 写前读取。 |
| **verifier** | 消费 verifier view + 正文机器视图 + 任务列表 + 检测结果，写入主线落地裁决建议与证据。 | 独立验收（chapter context verifier view、verdict set）。 |
| **repair** | 消费 repair view + verifier 失败项 + CLI 检测错误，输出最小修复正文。 | 修复循环（chapter context repair view、chapter update 重写）。 |

各角色通过 CLI 契约命令读取状态、提交候选、触发硬层校验；CLI 拒绝时停止流程，进入修复、补写、回退或人工处理。

> 切入点对应的具体 CLI 命令见 `contracts/cli/commands.md`；Packet 视图语义见 `docs/设计亮点-章契约与上下文包.md`。

## 4. 裁决存在性门禁

writer 只负责正文，不自评主线落地；verifier 消费 verifier view 与正文机器视图，写入裁决证据；CLI 在状态推进命令中只读裁决位和 hard 检查结果。

硬阻断规则：

- 裁决缺失、`achieved=0` 或 hard 违规都应结构化失败，防止"漏委派 verifier"被静默放过。
- 主线落地裁决必须绑定裁决时的章节正文 `content_hash`。
- 正文修复、重写或外部 hash 变化后，旧裁决自动失效（stale），不得继续作为进入 `review`/`approved` 的依据。
- 规则检查结果必须绑定被检查正文的 `content_hash` 与适用规则集版本；正文或规则变化后，旧检查结果不得用于状态推进。

> 裁决数据结构与 stale 保护见 `contracts/cli/verdicts.md`（SSOT）；状态推进门禁见 `contracts/cli/state-machine.md`。

## 5. 修复循环

verifier 或 CLI 检测失败时进入 repair 循环。repair 只修复失败项：

- 不扩大章节目标。
- 不重写已通过且无需改动的部分。
- 不修改冻结主线、卷目标或 hard rules。
- 修复后重新通过 CLI 写入正文，再重新检测和验证。

回退路径：

| 回退 | 语义 | 处理 |
|---|---|---|
| `review → drafting` | 正文需最小修复。 | 保留章契约和章节绑定，旧正文可作为修复输入；正文 hash 改变后旧规则检查结果和旧主线裁决自动失效。 |
| `review → outline` | 章契约、小节绑定或章节目标需重做。 | 必须清理或标记废弃与旧章契约绑定的检查结果、裁决、残余、四相日志和 thread 计划，避免被新草稿复用。 |

> 任何正文 hash 改变都会使旧规则检查和旧主线裁决失效，Spec 必须重新执行对应检测与验证，写入绑定当前 hash 的新裁决/检查结果。

## 6. 章后更新三类结果

章撰写完成后，CLI 不做文学判断，但必须在受控命令中更新小轮回产生的结构化结果。章后更新区分三类：

| 类别 | 内容 | 性质 |
|---|---|---|
| **权威事实** | 正文 hash、章节状态、事件终态、裁决位、hard 规则检查结果。 | 直接作为后续门禁和上下文来源。 |
| **当前快照** | 角色心理、关系、资源、支线局面、涌现弧线等。 | 可由 Spec/agent 推理后登记，必须标记 `inferred`、保留 `sourceRefs` 并支持过期检测。 |
| **overflow 索引** | 全量正文、长残余、低相关历史。 | 默认不进入下一章上下文，只进入可检索 manifest。 |

写下一章时，`chapter context` 应从上一章和滚动窗口带出最小集合（门禁与硬约束 P0、章契约 P1、上章残余 P1、裁决和风险 P1/P2、活跃 thread P1/P2、当前快照 P1/P2、背景摘要 P3、全量历史 P4/overflow）。

> 章后更新的部分实体（残余、四相日志）的落地状态见 `repository/dev-progress.md` §7.2 未实现实体清单。
