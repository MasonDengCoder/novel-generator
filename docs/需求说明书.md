> 本文档合并瀑布模式下的「软件需求规格说明书（SRS）」与「数据要求说明书」，为小型项目精简版。
> 是 M1 冻结的**需求基线**，后续所有设计、编码、测试的唯一依据。升格自早期需求文档（原始文件已删除）。

## 一、引言

### 1.1 目的

定义 `novel-generator` 工具包要解决的问题、功能边界与数据规则，为设计、编码、测试提供唯一依据。

### 1.2 范围

工具包用于在 Claude Code 上进行**托管式小说创作**：用户只参与大纲及规划，后续撰写全程 AI 托管。系统需控制 context 大小、prompt 生成、生命周期管理、创作元素管理，**使用一定要简单**。

### 1.3 术语

| 术语 | 含义 |
|------|------|
| 软层 / 硬层 | 软层=LLM 创作判断；硬层=确定性事实状态管理 |
| 史册 | 章节正文，答"发生了什么" |
| 日志 | 结构化遥测，答"如何运转" |
| 四极 | 世界的硬边界（力量上限、道德底线等） |
| 遁去其一 | 创作中自然涌现的活变数（人物/事件） |
| 四层嵌套轮回 | 创作奠基 → 创作周期 → 卷 → 事件 → 章节 的时间尺度建模 |

---

## 二、总体描述

使用 Claude Code 进行托管式小说创作：用户只参与大纲及规划，后续撰写全程 AI 托管。系统以《创作即创世》方法论为基础设计，并把方法论冻结为可执行规格，随版本演进。

## 三、功能性需求

### 3.1 软硬分层（FR-1）

把"LLM 创作判断"与"事实状态管理"分离：

- **FR-1.1** 软层产出**史册**（章节正文，答"发生了什么"）。
- **FR-1.2** 硬层产出**日志**（结构化遥测，答"如何运转"）。
- **FR-1.3** 依赖单向：软层 → 硬层；硬层对软层零感知，可脱离软层独立运行与测试。

### 3.2 安装与分发（FR-2）

- **FR-2.1 一键安装**：以 npm 安装软层时自动拉取硬层。
- **FR-2.2** 硬层亦可单独安装，供无 LLM 环境的外部程序驱动。

### 3.3 数据源唯一性（FR-3）

- **FR-3.1** 单一数据库持有全部状态（唯一数据源）。
- **FR-3.2** 正文本体**绝不入库**，库内只存弱引用 + 字数遥测。
- **FR-3.3 设定即视图**：世界设定圣经是数据库的派生渲染，而非独立膨胀的设定文件。

### 3.4 生命周期：四层嵌套轮回（FR-4）

创作流程必须被建模为四层嵌套的时间尺度，并守住**不可越级修正**铁律（高层修正必下传，低层禁止越级上报）：

```
创作奠基（确立大势：四极 / 主线 / 旁门，轮回开始前的基石）
   └─ 创作周期级（全书·灭相：终检 / 孤儿兜底 / 世界圣经 / 封档）
        └─ 卷级（每卷：系统处置遁去其一 吸收/拒绝/修补）
             └─ 事件级（每事件：因果清淤 / 标记待升级）
                  └─ 章节级（每章：四相撰写 / 只标记残余不修正）
```

- **FR-4.1** 遁去其一（涌现）须是带状态机的实体，遵循四级处置阶梯：章节级只标记 → 事件级轻量修正 → 卷级系统处置 → 周期级收束归档。
- **FR-4.2** 每章产出须受契约约束（须达成 / 禁止 / 情绪曲线），涌现致契约失效时按轻重分流处置。
- **FR-4.3** 每卷绑定一个 immutable 主线必达目标节点。卷收束前须**硬校验该目标是否达成**：未达成则禁止封卷。事件存在的意义是服务主线目标达成；主线卷级目标**绝不允许漂移**。
- **FR-4.4** 系统须在每章写作结束时产生遥测信号，度量本章叙事是否仍向本卷必达目标**收束**；信号用于**早期预警涌现把叙事拽离目标**，而非给主线设容差。预警命中的涌现交卷级处置（FR-4.6/4.7）修正或拒绝，直至目标达成。计算只读 `mainplot_nodes`，不修改。**该信号（及章级 must 是否落地的裁决）须由独立的隔离 subagent 产出（读正文 + must 约束 + `mainplot_nodes`），不得由当章写作者自评替代——防"LLM 说达成就达成"的自评盖章；收章命令只读已落库裁决、不自判（见详设 §2.2 `mainplot-landing-verifier`）。**
- **FR-4.5** 角色从 dormant 重新出场时，系统须由隔离 subagent 读取该角色完整 arc 历史 + 当前章场景上下文（时间/地点/进入状态），**推测出该角色此刻的合理当前态并入库为一条推测快照**；此后注入 context 的是这条紧凑快照而非完整历史，以降低 context 压力。推测快照须标记为推测态（区别于叙事实发），可审计、可被卷级修正，且不得越出四极。
- **FR-4.6** 涌现实体须支持完整处置闭环：章节级只标记 → 卷/事件级触发四维评分 → 基于评分给出四级处置阶梯建议 → LLM 执行并更新状态；整个流程须有 CLI 可查询的状态追踪。（源自 EXT-3，2026-06-09 升格，闭环断裂判定为核心缺陷）
- **FR-4.7** 处置阶梯须严格对应不可越级铁律：score ≥ 70（positive）可在事件级轻处置；50–69（neutral）在卷级系统处置；< 50（negative）优先卷级、跨卷则周期级收束；章节级在任何情况下均不得处置（只标记 `status=pending`）。

### 3.5 进度管理三落点（FR-5）

把"创作进度是否合法"做成可推进、可续接的状态机，须覆盖三处：

- **FR-5.1 创作周期进度**：奠基 → 编织 → 运行 → 封档的整体推进不可乱序。
- **FR-5.2 编织进度**：不能在首次运行就生成长达数百章的章节预设，须分批推进。
- **FR-5.3 写作进度**：单次任务仅完成 1–2 章，后续任务须能自动续上。

## 四、数据要求（合并自数据要求说明书）

### 4.1 数据源与边界

- **DR-1** 全部状态存于单一 SQLite 数据库 `index/novel.db`，为唯一真相源。
- **DR-2** 正文本体永不入库；DB 只存 `prose_ref`（弱路径引用）+ `word_count`（字数遥测）。
- **DR-3** 世界圣经（Bible）无独立存储，是 DB 的派生视图（core / active / dormant / full）。

### 4.2 数据结构演进规则

- **DR-4 严格增量**：数据结构只增不改不删，结构冻结后由测试守护。
- **DR-5** schema 只允许 `CREATE TABLE IF NOT EXISTS`，永不 ALTER/DROP。

### 4.3 数据分层（与四层轮回对应）

数据按 5 个 schema 分片增量叠加，逻辑映射见详细设计；需求层面的约束为：

| 分片 | 承载的创作概念 | 主要数据对象 |
|------|--------------|------------|
| layer1 | 奠基（定数/边界/旁门） | 阶段进度、四极边界、主线节点；支线/伏笔/爽点/承诺 |
| layer2 | 编织（卷→事件→节→章） | 卷、事件、小节、章、预设、大轮回；涌现/弧线 |
| layer3 | 写作（章内四相） | 章写作、章残余、监测信号、相位日志 |
| layer4 | 封档 | 创作周期、终检信号、创作日志归档 |
| layer5 | 横切绑定（为 LLM 而生） | 章级线索绑定 |

- **DR-6** 创作元素（支线/伏笔/爽点/承诺/涌现/弧线/线索绑定）虽随对应 layer 建表，但运行时读写一律经唯一入口管理，不绕过直接触碰元素表。
- **DR-7** 卷必达目标达成状态须以结构化数据落 layer2（卷级）；服务于目标收束的章级遥测信号落 layer3。封卷硬校验读取目标达成状态，未达成阻断封卷。
- **DR-8** 角色重激活时，隔离 subagent 推测出的角色当前态须作为一条标记为推测态的 arc 快照入库；`chapter_threads` 中 `action=reactivate` 的条目，由 `pre-write-chapter.sh` hook 注入这条紧凑快照，而非完整 arc 历史，不计入 bible 三层预算。

## 五、约束与原则（非功能性需求）

- **NFR-1 简单优先**：硬层零第三方依赖，无构建步骤、无 linter 配置。
- **NFR-2 数据结构严格增量**：只增不改不删，结构冻结后由测试守护。
- **NFR-3 可独立、可测试**：硬层不依赖软层即可运行与测试。
- **NFR-4 容错降级而非阻断**：异常时静默降级，绝不阻断写作。
- **NFR-5 编排可靠性边界**：确定性网覆盖"事实存储 / 越级处置 / 机械动作"（强保证），但**不覆盖**主控 LLM 的流程编排（按时调 skill、委派 agent）与判定质量。其中"漏委派主线裁决者"由 `prose end` CLI 存在性门禁兜底（详设 §2.4），其余漏委派与判定质量为已声明的残余风险，靠软层补偿层缓解而非钢性消除。
