# 小说创作工具系统 — 需求说明书（简化版）

> 核心目标：在有限上下文中，可靠地告诉 LLM“这一章应该怎么写”，并把长期必须记住的世界状态交给确定性工具保存。

---

## 1. 系统要解决什么问题

长篇小说创作需要长期记住世界设定、主线、人物状态、章节结果和卷级目标。LLM 容易遗忘、误判或自我说服，因此不能把这些长期状态只放在对话上下文里。

本系统将工作拆成两部分：

- **CLI（`novel`）**：保存世界状态，是唯一可信的世界日志入口。
- **Spec**：驱动创作流程，调用 LLM 写作、验证，并通过 CLI 读写世界状态。

最终产出的章节正文，就是这个世界按时间展开后的结果。

---

## 2. 核心原则

### 2.1 CLI 是唯一世界入口

所有世界状态必须通过 `novel` 命令读写。

Spec、Web 或其他外部系统不得直接读写底层数据库、正文文件或 CLI 内部模块。

### 2.2 LLM 不负责长期记忆和硬判断

凡是“忘了就会崩”的内容，都必须落到 CLI 管理的数据中。

凡是可以确定性检查的规则，都应由 CLI、Hook 或脚本执行，不依赖 LLM 自觉遵守。

### 2.3 创作可以自由，主线不能漂移

写作过程中允许支线、伏笔、爽点和涌现变化，但每卷必须朝绑定的主线目标收束。

卷目标未达成时，不允许封卷。

### 2.4 写作与验证必须分离

写作代理只负责写正文。

主线落地、越界、整体一致性等判断，必须由独立验证流程完成。

写作者不得自评。

---

## 3. CLI 需求

CLI 是“世界状态日志”，负责保存、校验和保护所有硬层数据。

### 3.1 CLI 必须管理的数据

CLI 至少需要管理：

- 项目初始化与世界信息。
- 世界观设定、四极边界、设定视图。
- 主线节点、支线、伏笔、爽点、读者承诺。
- 卷、章节、卷目标绑定、章节正文。
- 章节状态机。
- 章末残余、四相日志、thread 绑定。
- 涌现记录及处置状态。
- 角色、弧光、活跃状态、重激活快照。
- 卷级归档、封典终检。
- 章级主线落地裁决。
- 面向 Web 可视化的只读机器输出。

### 3.2 章节状态机

章节状态只能这样流转：

```text
outline → drafting → review → approved
  ↑               │
  └── 需修改回退 ─┘
```

要求：

- `approved` 是终态，不得再修改正文或状态。
- 没有章级主线落地裁决时，不得进入 `review`。
- 主线落地裁决失败时，不得进入 `review` 或 `approved`。
- 状态流转失败必须返回非零退出码和明确错误。

### 3.3 涌现处置顺序

涌现必须按顺序处置：

1. 评分
2. 决策
3. 执行
4. 留痕

评分必须包含明确维度，且必须完整覆盖 `impact`（影响范围）、`coherence`（一致性）、`cost`（吸收成本）和 `urgency`（处置紧迫度）；决策必须基于完整评分结果与处置层级。任何跳步都必须被 CLI 拒绝，任一未完成处置和留痕的涌现不得封卷。

### 3.4 CLI 必须硬阻断的情况

CLI 必须拒绝以下操作：

- 章节级命令修改主线、世界边界或卷目标。
- 修改 `approved` 章节。
- 章级裁决缺失时推进章节到 `review`。
- 主线落地裁决失败时推进章节。
- 涌现处置跳步。
- 涌现未处置完成时封卷。
- 卷目标未达成时封卷或归档。
- 非封典阶段执行终检。
- 外部代码绕过命令行调用 CLI 内部模块。

### 3.5 数据一致性

CLI 写入失败不得破坏已有数据。

章节正文采用“文件存储 + SQLite 元数据索引”的方式保存。CLI 写正文时必须同步更新正文 hash、字数、状态和元数据。

如果用户绕过 CLI 修改正文文件，CLI 必须能检测到，并拒绝继续或要求显式修复。

---

## 4. Spec 需求

Spec 是“世界运行引擎”，负责按方法论驱动 LLM 创作。

### 4.1 Spec 只能通过 CLI 访问世界状态

Spec 可以执行 `novel` 命令读取设定、章节、约束和状态，也可以通过 `novel` 命令写入正文、裁决、残余、涌现等数据。

Spec 不得：

- 直接读取 SQLite。
- 直接读取或修改 `.novel/content` 下的正文文件作为状态来源。
- import / require / link CLI 内部模块。
- 依赖 CLI 内部路径、表结构或 Rust 模块名。
- 自行绕过 CLI 判断章节、卷或封典是否通过。

### 4.2 创作流程

#### 开天阶段

- 根据用户构想生成世界设定和四极边界。
- 通过 CLI 写入世界基础数据。
- 推进到编织阶段。

#### 编织阶段

- 生成主线节点、支线、伏笔、爽点和读者承诺。
- 生成卷结构和每卷必达目标。
- 生成章节大纲。
- 通过 CLI 创建卷和章节占位。
- 推进到运行阶段。

#### 运行阶段

对每章按顺序执行：

1. **章节预检**：确认世界、创作周期、卷、章节、小节、事件、主线冻结与卷目标均处于可写作状态；不满足则停止。
2. **获取章节关联信息**：通过 CLI 获取设定视图、thread 绑定、绑定事件/小节、出场角色、前章残余、卷目标、强制限定规则与未闭环项。
3. **编译 Chapter Context Packet**：生成 writer view，必须包含预算、优先级、`sourceRefs`、压缩记录和 overflow manifest；核心上下文超限时不得继续写作，应建议拆章或压缩规则视图。
4. **生成并固化章节目标任务列表**：列出本章必须达成、必须避免、必须承接、必须留下的任务与验收证据要求，作为写作与验证之间的契约。
5. **撰写章节正文**：写作代理只消费 writer view 和固化任务列表，生成正文及残余/四相/涌现候选，不得自评主线落地。
6. **通过 CLI 写入正文**：使用 `novel chapter update <id> --content <file>` 写入正文，由 CLI 更新 SQLite 元数据、hash、字数与更新时间。
7. **确定性检测**：触发撞极检测、收束遥测、hard constraint check、正文 hash、格式、字数和引用完整性检查；失败则阻断。
8. **独立主线落地验证**：验证代理消费 verifier view、正文、任务列表与检测结果，写入章级裁决。
9. **修复循环**：裁决或整体验收失败时，使用 repair view 和失败项进行最小闭环修复，重新写入、检测和验证。
10. **提取残余、四相日志与涌现候选**：通过 CLI 写入残余和四相日志；新增人物、物件、地点、冲突、期待等先作为涌现候选记录。
11. **更新关联数据状态**：正文通过基本验收后，才通过 CLI 更新事件、支线、伏笔、爽点、承诺、角色状态、弧光和后续 thread binding。
12. **状态推进与归档**：依次进入 `review`、`approved`、archive，并更新创作进度；状态推进和归档必须最后执行。

#### 大轮回阶段

当一卷所有章节都 `approved` 后：

1. 先完成所有涌现处置。
2. 检查卷目标是否达成。
3. 执行卷级监测。
4. 生成 dormant 角色的重激活快照。
5. 封卷并归档。
6. 如果是最终卷，进入封典阶段。

#### 封典阶段

- 执行终检。
- 终检通过后标记全周期完成。

### 4.3 Chapter Context Packet 需求

Chapter Context Packet 是运行阶段的核心输入产物，用于在有限 context 预算内描述“本章应该怎么写”。它不是权威世界状态，只是从 CLI 权威状态派生出的阶段性受控视图。

基本要求：

- 每章写作前必须生成或获取 Chapter Context Packet。
- Packet 输入必须来自 `novel` CLI 的稳定输出，不得来自 SQLite、`.novel/content` 或 CLI 内部模块。
- 推荐由 `novel chapter context` 输出 CLI canonical Chapter Context Packet；Spec 只消费该机器结构并渲染 prompt，不得自行重排、删除、重压缩或补全 P0/P1 片段。
- Packet 必须支持 `writer`、`verifier`、`repair` 三种视图。
- Packet 必须包含预算上限、预算使用、片段优先级、`sourceRefs`、压缩级别、audit 与 overflow manifest。
- Packet 超限时必须压缩、省略并记录，或结构化失败；不得静默截断。

最小内容：

1. 本章写作目标与 ChapterIntent。
2. 所属卷目标、主线压力与禁止偏离方向。
3. 绑定事件、小节、地图/地点、时间、当前阶段。
4. 出场角色当前状态、目标、情绪、冲突、隐瞒信息与允许变化范围。
5. 前章残余、未清线索、情绪余波和必须承接的因果。
6. 相关支线、伏笔、爽点、读者承诺。
7. 本章 scope 相关的四极硬规则、强制限定规则、禁止事项与风格规则。
8. 可吸收或待处置的涌现候选。
9. 写作约束：目标字数、叙事视角、节奏、情绪曲线、输出格式。
10. 写后验证提示：主线落地证据要求、撞极检测点、收束遥测标准。

超限处理：

- P0 硬约束超限：视为配置错误，禁止生成章节，要求压缩规则视图或拆分规则 scope。
- P0 + P1 最小核心超限：视为章节设计过载，禁止生成章节，建议拆章、减少绑定事件或缩小本章目标。
- P2 / P3 超限：按统一压缩阶梯处理，从 `full` 降为 `focused`、`summary` 或 `omitted`，压缩后必须记录原始来源、压缩级别和原因。
- P4 默认不进入 prompt，只进入 overflow manifest。
- Bible / setting 必须支持分层渲染，避免全量注入挤压章契约、角色状态、残余和验证标准。

### 4.4 Spec 的容错要求

Spec 必须：

- 捕获每次 CLI 命令的退出码和输出。
- CLI 返回失败时立即中断当前流程。
- 支持代理失败重试，重试上限可配置。
- 支持断点续传，从最早未完成章节继续。
- 记录结构化日志，便于排查失败原因。

---

## 5. Web 可视化预留

未来 Web 可视化可以展示世界状态、章节进度、主线落地、涌现处置、角色弧光和归档报告。

但 Web 也必须遵守：

- 不直接读写底层存储。
- 只能通过 CLI 提供的受控机器输出访问世界状态。
- 默认只读。
- 如果未来开放写操作，也必须复用 CLI 的状态机、权限和硬阻断。
- 输出结构必须带版本号，便于前端兼容。

---

## 6. 非功能需求

- **跨平台**：支持 macOS、Linux、Windows。
- **可靠性**：命令失败不得产生脏数据。
- **可恢复性**：异常中断后可以检测并恢复或拒绝不一致状态。
- **幂等性**：重复执行同一命令不得产生意外副作用。
- **可测试性**：CLI、Spec 和契约输出都必须可测试。
- **清晰错误**：禁止静默失败，所有失败都要说明原因。

---

## 7. 验收标准

系统至少通过以下验收：

1. `novel init <name>` 能创建完整世界结构。
2. 章节初始状态为 `outline`。
3. 重名章节或重复实体创建会报错。
4. Spec 能通过 CLI 将章节从 `outline` 推进到 `approved`。
5. 撞极检测失败时，章节不能通过验证。
6. 章级主线落地裁决缺失时，章节不能进入 `review`。
7. 章级主线落地裁决失败时，章节不能进入 `review` 或 `approved`。
8. 卷目标未达成时，不能封卷。
9. 涌现处置跳步会被拒绝。
10. 涌现未全部处置完成时，不能封卷。
11. `approved` 章节不能被修改。
12. CLI 内部模块不能被外部代码直接调用。
13. Spec 在 CLI 命令失败时会停止，不产生脏数据。
14. 中断后重启，Spec 能从断点继续，不重复生成已完成章节。
15. CLI JSON 输出结构稳定，并带 schema/version 信息。
16. 每章写作前能生成或获取 Chapter Context Packet，并区分 writer/verifier/repair 视图。
17. Context Packet 超预算时不会静默截断，而是压缩、省略并记录 audit/overflow，或结构化失败。
18. Spec 在写前生成并固化章节目标任务列表，写后按任务列表验收。
19. 验收失败的章节不会先污染事件、角色、伏笔、承诺等关联状态。
20. 规则检查结果必须绑定正文 hash 与规则集版本；正文或规则变化后，旧检查结果不得用于状态推进。
21. 主线落地裁决必须绑定正文 hash；正文修复或重写后，旧裁决不得用于进入 `review` / `approved`。
22. `approved` 章节允许执行受控归档，但不得再修改正文、裁决、残余、四相日志或 thread binding。

## 附录：方法论关键词

- **主线**：不可改的大势。
- **支线 / 伏笔 / 爽点**：可调整的小势。
- **四极边界**：世界允许变化的边界。
- **涌现**：写作中出现的意外变化，需要记录和处置。
- **小轮回**：章节之间的推进与残余传递。
- **大轮回**：卷末的全局检查、处置和归档。
- **封典**：全书终检和最终归档。
