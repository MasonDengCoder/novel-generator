# 小说创作工具系统 — 项目整体架构

> 本文定义项目级分层架构、优缺点、技术选型、技术限制、能力边界与功能边界。设计亮点已抽离至 `docs/设计亮点-*.md` 五份独立文件；CLI 硬层落地见 `docs/CLI架构设计.md`；Spec 数据流见 `docs/Spec架构设计.md`；命令契约以 `contracts/cli/commands.md` 为 SSOT。

---

## 1. 核心问题

本系统实际解决的核心问题是：

> 如何在有限 context 中，尽可能完整、清楚、可靠地描述"本章应该怎么写"，并在写后通过硬层校验与独立验证把章节拉回正轨。

长篇小说创作不是一次性文本生成，而是一个持续运行的世界状态系统。LLM 适合进行创作、推理、审校和修复，但不适合承担长程状态记忆、事务一致性、权限边界和硬门禁。因此系统必须把"忘了就崩"的内容下沉到确定性硬层，把"需要创造性判断"的工作留给软层编排。

整体目标不是把更多资料塞进 prompt，而是在有限 context 内保证：

1. 最关键的信息一定在。
2. 次关键的信息尽量在。
3. 低价值信息可追溯地不在。
4. 写后能判断哪里偏了、为什么偏、如何修复。
5. 通过 CLI 让可机械判断的失败硬阻断，而不是依赖 LLM 自觉。

## 2. 总体分层

> **SSOT 边界**：本节为对外架构权衡说明，含方法论与存储实现细节层，分层粒度较细。稳定的三层分层定义（Spec 运行层 / CLI 硬层 / 存储层，CLI Contract 作为软硬层稳定边界）以 `repository/architecture.md` §分层模型为 SSOT；本节五层口径与 SSOT 互补，若层划分冲突以 `repository/architecture.md` 为准。

```text
方法论层：《创作即创世》
  │
  │  转译为阶段、规则、流程、验证标准
  ▼
软层：Claude Code LLM Harness / Spec 运行层
  │
  │  只通过 novel 命令查询和提交世界状态
  ▼
契约层：CLI Contract
  │
  │  固定命令、JSON schema、错误码、golden examples
  ▼
硬层：Rust novel-cli
  │
  │  通过 service / guard / repository / storage 管理状态
  ▼
存储层：SQLite + 正文文件
```

### 2.1 方法论层

方法论层定义"世界如何运行"：创作周期（开天、编织、运行、封典、完成）、四层轮回（章节、事件、卷、创作周期）、硬规则（大势不可改、遁去其一仍在四极、不可越级修正）、创作对象（主线、支线、事件、小节、章节、角色、伏笔、爽点、承诺、残余、涌现）、验证对象（主线落地、撞极、收束遥测、规则违规、涌现处置、卷末闭环）。方法论层只定义原则和约束，不直接读写状态。

### 2.2 软层：Claude Code LLM Harness / Spec 运行层

软层负责把方法论落成可调用的创作流程：组织 prompt、上下文包、任务列表和验证标准；调度 writer/verifier/repair/extractor 等 LLM 执行实例；在正确阶段调用 `novel` CLI 查询权威状态、提交结果、触发硬层校验；在 CLI 拒绝时停止流程，进入修复、回退或人工处理。

软层不得：存储创作状态作为权威来源；直接读取或修改 SQLite；直接读取或修改 `.novel/content` 作为状态来源；解析硬层内部文件布局；import/require/link CLI 内部模块；自行判断章节是否可进入 `review`/`approved`，或卷是否可归档。这些判断必须由 CLI service/use-case 与 guard 执行。

> Spec 运行层落地状态见 `repository/dev-progress.md` §7.1。

### 2.3 契约层：CLI Contract

CLI Contract 是软硬层之间的稳定边界，负责约束：命令语法与参数语义、`--json` 输出结构、`schemaVersion`、结构化错误对象/错误码/退出码、实体 ID/引用规则/sourceRefs、golden examples/JSON schemas/contract tests。契约层让 CLI 内部实现可以演进，而 Spec、Web、脚本和 LLM 消费方仍只依赖稳定命令与稳定 JSON。

### 2.4 硬层：Rust novel-cli

硬层是 `novel` CLI，负责世界状态读写、状态机与权限矩阵、事务一致性、正文 hash 与外部改动检测、错误码与非零退出码、章节/卷/封典门禁、归档与冻结、防绕过、稳定 JSON 输出与 CLI Contract。硬层不负责：生成章节正文、调度 LLM、编排 Skills、决定 prompt 形态、保存软层运行时上下文。CLI 可提供面向 Spec 的只读受控上下文视图，但这些视图仍是 CLI 命令输出，不是外部 SDK 或内部存储入口。

### 2.5 存储层：SQLite + 正文文件

存储层是硬层实现细节：SQLite 是权威元数据、状态机、索引、引用、hash、归档状态的来源；章节正文使用文件存储，SQLite 记录路径引用、hash、字数、更新时间和状态；`.novel/` 内部路径、SQLite schema、migration 文件名、Rust module 名称都不是稳定契约。外部系统只能通过 `novel` 命令访问这些数据。

## 3. 分层架构的优缺点

### 3.1 优点

| 优点 | 说明 |
|------|------|
| 状态权威清晰 | 只有 CLI 接受后的数据才是世界状态，避免 prompt、缓存、草稿互相污染。 |
| 长程一致性更可靠 | 状态机、门禁、hash、归档、引用完整性由确定性硬层执行。 |
| LLM 使用更聚焦 | LLM 只负责创作、判断、修复和总结，不背负数据库一致性与权限判断。 |
| 可审计 | CLI 输出 sourceRefs、hash、schemaVersion、错误码、audit 与 overflow，便于复盘。 |
| 可演进 | CLI 内部 SQLite schema、文件布局、Rust 模块可变，只要 CLI Contract 不变，Spec 不受影响。 |
| 可测试 | 命令、JSON schema、退出码、golden examples、contract tests 可独立验证。 |

### 3.2 代价

| 代价 | 说明 | 缓解方式 |
|------|------|----------|
| 流程更重 | 章节生成不是一次 prompt 完成，而是预检、编译上下文、写入、检测、验证、修复、回写。 | 用 Skill/Hook 自动化固定步骤，把复杂度留在流程而非用户手上。 |
| 契约维护成本 | CLI 与 Spec 必须同步命令、JSON schema、错误码。 | 建立 `contracts/cli`、golden examples 与 contract tests。 |
| 初期实现成本更高 | Rust CLI、SQLite、正文文件一致性、状态机都需要先搭建。 | 先实现最小闭环命令，再逐步扩展实体族。 |
| 软硬边界需要纪律 | Spec 容易为了方便直接读文件或缓存状态。 | 通过 Rules/Hook/测试和文档明确禁止绕过 CLI。 |
| 部分判断仍需 LLM | 审美、主线是否"有效落地"、修复方案等无法完全机械化。 | LLM 给建议或裁决证据，CLI 负责记录、门禁和结构化阻断。 |

### 3.3 不采用单层架构的原因

| 方案 | 问题 |
|------|------|
| 纯 LLM / 纯 Spec | 容易遗忘状态、绕过门禁、静默截断 context，难以保证归档与回滚一致性。 |
| 纯 CLI / 纯规则引擎 | 可以可靠管理状态，但不能承担高质量创作、语义审校和复杂修复。 |
| 直接让 Spec 调 SQLite | 短期方便，长期会把 SQLite schema 变成隐形公开 API，破坏 CLI Contract 与防绕过。 |
| 直接把正文全部存 SQLite | 有事务优势，但牺牲作者可读性、备份便利和 Markdown 工作流。 |

## 4. 技术选型

### 4.1 CLI 主体：Rust

选择 Rust：强类型 enum/match 适合表达状态机与权限门禁；可发布跨平台单文件二进制；与 SQLite 集成成熟；启动快适合 Spec 高频子进程调用。推荐技术栈：clap、rusqlite、refinery 或内置 migration runner、serde/serde_json/serde_yaml、thiserror/anyhow、time、comfy-table、assert_cmd/predicates/tempfile。

### 4.2 正式存储：SQLite + 正文文件

SQLite：百万字长篇积累大量实体与图谱关系数据；提供事务、索引、约束、迁移；状态机推进、封卷、归档等硬阻断需可靠事务。正文用文件 + SQLite 索引：Markdown 可读可备份；SQLite 记录引用/hash/字数/状态/冻结标记；CLI 能检测绕过修改。

### 4.3 Spec 运行层：Claude Code 原语

Claude Code 原语分配原则：Rules 跨阶段不变式；Hooks 固定时机确定性动作；Skills 阶段性多步流程；Subagents 读完即弃/重上下文/独立验证。当前 Spec 文档只描述数据流转和 LLM 切入点，原语能力事实依据见 `reference/参考-ClaudeCode原语能力边界.md`。

### 4.4 Monorepo 与目录边界

项目物理上保留在 monorepo，逻辑拆分为 CLI 硬层项目与 Spec 运行层项目。目录边界与结构见 `CLAUDE.md` §5 与 `repository/architecture.md`。先不拆独立仓库，避免 CLI 契约尚未稳定时增加跨仓库同步成本。

## 5. 技术限制

### 5.1 LLM 与 context 限制

LLM 输出不具备事务性，不能作为权威状态写入；会遗忘、压缩、误读或过度泛化历史；prompt 超限时不得静默截断，必须记录 audit 与 overflow manifest；写作者不得自评主线落地，验证必须由独立实例完成。

### 5.2 Claude Code 原语限制

Rules 适合短小不变式，不适合承载完整方法论；Hooks 适合机械门禁，不适合复杂 LLM 创作判断；Skills 适合流程编排但不能成为权威状态存储；Subagents 适合独立读取验证，读完即弃不拥有状态写权限。

### 5.3 CLI 与本地存储限制

CLI 无法阻止用户从操作系统层面直接编辑 `.novel/` 文件，只能通过 hash、状态机和归档标记检测并拒绝继续；SQLite 与文件系统无法天然提供跨 DB 与文件的完美原子提交，实现必须保证失败后可检测、可修复或拒绝不一致状态；本地 CLI 默认面向单机项目级写锁，不承诺多用户实时协作；`.novel/` 内部路径、SQLite schema、migration 文件名不是公开契约。

### 5.4 契约与版本限制

Spec、Web、脚本只能依赖 CLI Contract，不得依赖实现细节；CLI Contract 一旦发布需兼容演进，破坏性变更必须通过版本升级与迁移策略处理；JSON 输出必须包含 `schemaVersion` 并通过 contract tests 验证。

## 6. 能力边界

### 6.1 状态权威边界

```text
未通过 CLI 写入的内容 = 运行时中间产物
通过 CLI 写入且被硬层接受 = 世界状态
```

Spec 可以产生 prompt、Context Packet、Task List、verifier 报告、repair 建议、emergent 候选、摘要与分析，但只有通过 CLI 写入并被硬层接受后才成为世界状态。

### 6.2 读写边界

所有新状态必须通过 CLI 写命令完成（具体命令见 `contracts/cli/commands.md`）：章节正文、主线裁决、涌现处置、状态流转等均经 CLI 受控命令写入。所有状态读取必须通过 CLI 输出：人读输出供作者检查，JSON 输出供 Spec/Web/脚本/LLM 消费，长文本通过视图/摘要/分块/受控上下文包输出避免软层直接读取内部文件。

### 6.3 判断边界

| 判断类型 | 负责层 |
|----------|--------|
| 状态机是否合法 | CLI |
| 权限/阶段是否允许 | CLI |
| 正文 hash 是否被绕过修改 | CLI |
| hard 规则是否阻断推进 | CLI |
| context 是否超预算且有无 audit | CLI 或 Spec 编译器，但必须结构化输出 |
| 章节正文怎么写 | LLM writer |
| 主线落地语义证据建议 | 独立 verifier |
| 修复方案怎么最小闭环 | LLM repair |
| 是否接受状态推进 | CLI guard |

## 7. 功能边界

### 7.1 本项目范围内

- 小说世界初始化与生命周期阶段管理。
- 设定文档登记与强制限定规则管理。
- 主线、支线、事件、小节、章节、角色、伏笔、爽点、承诺、残余、涌现等世界状态管理。
- Chapter Context Packet 的受控查询或编译输入。
- 单章写作流水线：预检、上下文、任务、写作、写入、检测、验证、修复、回写、推进、归档。
- 大轮回、卷末监测、涌现处置、封典终检。
- CLI Contract、JSON schema、错误码、golden examples 与 contract tests。
- 后续 Web/view/serve 的受控只读出口。

### 7.2 暂不承诺

暂不承诺：CLI 直接生成高质量章节正文；CLI 内置 LLM 调度器；外部 SDK/API 绕过 CLI 使用内部模块；多用户实时协作、云同步、权限服务器；直接暴露 SQLite schema 给 Spec 或 Web；自动解决所有审美问题；Web 可视化写入绕过 CLI guard。

> §7.1 列出的世界状态管理实体的实现覆盖面（哪些已落地、哪些为规划态）与设计覆盖面反推对照见 `repository/dev-progress.md` §7.0 与 §7.2，不在本文件重复列举。

## 8. Chapter Context Packet 在整体系统中的位置

Chapter Context Packet 是每章写作前从 CLI 权威状态派生的受控上下文视图，在有限 context 预算内描述"本章应该怎么写"。它不是世界状态本身，由 CLI 命令输出 canonical 机器结构，Spec 只消费并渲染为 prompt。

> Packet 的设计语义（三种视图、五层×五优先级矩阵、预算规则、压缩阶梯、audit/overflow、诚实省略机制）已抽离至 `docs/设计亮点-章契约与上下文包.md`。

## 10. 标准章节写作流水线

逐章运行拆成多步而非"拿 context 直接写"。流水线的阶段图、三角色职责、写验分离原则、修复循环与 hash/stale 失效规则已抽离至 `docs/设计亮点-写作流水线与写验分离.md`。

关键原则：写前阶段只准备和确认不直接生成正文；写作代理不得直接修改世界状态；写后先执行确定性检测再执行独立语义验收；验收失败时只修复 verifier 指出的偏移不扩大章节目标；正文通过基本验收前不应更新事件、角色、伏笔、承诺等结构化世界状态；状态推进和归档必须最后执行。

## 11. 验收边界

CLI 项目验收关注：命令是否正确；状态机是否硬阻断；SQLite 与正文文件是否一致；hash 是否能检测绕过修改；错误码与 JSON 输出是否稳定；失败是否回滚；外部是否无法通过公开入口绕过 CLI。

Spec 项目验收关注：是否只通过 `novel` 子进程调用访问世界状态；是否使用 `--json` 消费机器输出；是否正确处理非零退出码；CLI 拒绝时是否停止流程并进入修复/回退；是否不依赖 SQLite、正文文件路径或 CLI 内部模块。

契约测试负责验证：固定输入对应稳定 JSON schema；Spec mock 能消费 CLI 输出；Spec mock 能捕获 CLI 非零退出码并中断；CLI 内部存储变更不影响 Spec，只要 CLI Contract 不变。
