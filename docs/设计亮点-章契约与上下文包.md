# 设计亮点：章契约与上下文包

> 本文档记录设计语义，不含命令语法。命令契约以 `contracts/cli/commands.md` 为唯一事实来源（SSOT）；实现状态以 `repository/dev-progress.md` 为准。涉及未实现实体标注"规划态"。

> 抽离来源：`docs/CLI架构设计.md` §6.5 章契约三档约束、§9 章节上下文包；`docs/Spec架构设计.md` §6 Chapter Context Packet 数据流。

## 1. 章契约三档约束

章契约是章节上下文包的核心输入，使用三档约束平衡纪律与涌现：

| 约束类型 | 语义 | 硬层要求 |
|---|---|---|
| `must` | 本章必须落地的目标或禁止错过的主线节拍。 | 不可静默降级；主线相关项必须带 `mainplotNodeId`、`verifyMethod` 与 sourceRefs，裁决位由 verifier 或检查流程写回。 |
| `may_deviate` | 允许在边界内变化的小势、误判、局部处理方式。 | 只能在四极、卷目标和冻结主线边界内偏离；偏离后仍需保留 sourceRefs 供验证。 |
| `encourage_surprise` | 鼓励意料之外但情理之中的涌现。 | 只能生成候选或 pending 涌现，不得直接改写主线、卷目标或核心设定。 |

> 三档约束的 `sourceRefs` 字符串格式与实体类型前缀见 `contracts/cli/entity-ids-sourcerefs.md`（SSOT）。

> **实现状态**：章契约表（must/may_deviate/encourage_surprise/场景配置/预期出口）无实体表，`chapter context` 命令输出有数据支撑的 P0/P1 子集，章契约层输出 `overflow.omitted`（reason=`no_data_backing_table`，对应实体表未落地）。落地状态见 `repository/dev-progress.md` §7.2。

## 2. Chapter Context Packet 定位

Chapter Context Packet 是每章写作前从 CLI 权威状态派生出的阶段性受控上下文视图，用于在有限 context 预算内描述"本章应该怎么写"。

- 它**不是**世界状态本身，只是从权威状态派生的受控视图。
- 由 CLI 命令输出 canonical 机器结构，Spec 只消费该结构并渲染为 prompt。
- Spec 不得自行重排、删除、重压缩或补全 canonical packet 的 P0/P1 片段；不得用缓存、对话记忆或推测内容补全 omitted 片段。

```text
世界权威状态（CLI / SQLite / 正文索引）
  │
  │  稳定查询、relatedness、view render
  ▼
Chapter Context Packet
  │
  │  渲染为 writer / verifier / repair prompt
  ▼
LLM 写作、验证、修复
```

## 3. 三种视图

| View | 消费者 | 重点 | 不应包含 |
|---|---|---|---|
| `writer` | 写作代理 | 写什么、怎么写、不能写什么。 | 大量验证细则、长篇历史全文。 |
| `verifier` | 独立验证代理 | 检查什么、如何判定、证据要求。 | 风格铺垫、写作鼓励、无关背景。 |
| `repair` | 修复流程 | 哪些偏移必须修复、哪些冻结项不可改、可改范围在哪里。 | 全量世界观、无关支线、未失败的低风险内容。 |

> 受控 view 名及其机器语义见 `contracts/cli/views-scopes.md` §A 组 4（SSOT）。三种视图可共享同一批 sourceRefs，但内容组织、预算分配和压缩方式不同。

## 4. 五层 × 五优先级矩阵

上下文包按五层组织，每层按优先级装填与压缩：

| 层 | 内容 | 处理方式 |
|---|---|---|
| Authority / Gate | hard 规则、冻结主线、卷目标、状态、hash、裁决位、检查结果 | 直接读取权威状态，不推理。 |
| Chapter Contract | 本章 `must`、`may_deviate`、`encourage_surprise`、入口状态、场景配置、预期出口 | 作为 writer/verifier/repair 的章级契约。 |
| Snapshot | 角色当前态、支线局面、涌现弧线、资源/代价、重激活状态 | 可为确定性派生或 Spec/agent 推理后登记，必须标记 `derived`/`inferred`。 |
| Thread Binding | 本章绑定元素、相关度、动作 `plant|advance|advance_milestone|payoff|reactivate` | 按动作优先级和相关度裁剪。 |
| Overflow / Retrieval | 全量历史、低相关归档内容、长设定、长正文 | 默认只给 manifest、摘要和补取方式。 |

| Priority | 内容 | 超限策略 | 压缩阶梯 |
|---|---|---|---|
| P0 | 硬规则、冻结目标、输出协议、验证标准 | 超限失败。 | 不可压缩 |
| P1 | 章契约最小集、绑定事件、小节、入口状态、上章残余、关键角色快照 | 最小版本放不下则失败并建议拆章。 | 不可压缩 |
| P2 | 强相关支线、伏笔、承诺、风险记录、活跃 thread | 在保留 sourceRefs 的前提下逐级压缩。 | `full → focused → summary` |
| P3 | 背景、远因、风格样例、dormant 或重激活快照 | 摘要化或 omitted。 | `focused → summary → omitted` |
| P4 | 全量历史、低相关归档内容 | 默认只进入 overflow manifest。 | 默认 `omitted` |

CLI 生成上下文包时先装填 P0 和 P1_min，再按预算处理 P2/P3。每次压缩或省略都必须记录在 `audit` 或 `overflow` 中。

## 5. 预算与超限处理

context 超限不得静默截断，也不得从尾部硬砍。超限处理采用统一压缩阶梯：`full → focused → summary → omitted`。

- **P0 超限**：视为配置错误，禁止生成章节，要求压缩规则视图或拆分规则 scope。
- **P0 + P1 最小核心超限**：视为章节设计过载，禁止生成章节，建议拆章、减少绑定事件或缩小本章目标。
- **P2 / P3 超限**：按统一压缩阶梯处理，压缩后必须记录原始来源、压缩级别和原因。
- **P4**：默认不进入 prompt，只进入 overflow manifest。
- 任何 compressed 或 omitted 片段都必须在 `audit` 或 `overflow` 中记录原因、来源、压缩级别和可重新查询的 CLI 引用。

预算超限是"可恢复前置阻断"：返回非零退出码 + 结构化错误对象（含 `budget` limit/used 与 `failures` 超限层估算），让 Spec 区分"硬前置阻断"与"预算不足可恢复"。Spec 可据此调高预算或拆章后重试。

## 6. audit 与 overflow

每次编译都应产出审计信息，Spec 必须把 `audit` 和 `overflow` 当作流程控制输入而非旁注：

```json
{
  "chapterId": "ch-038",
  "view": "writer",
  "budget": {"limit": 60000, "used": 54820, "reserved": 5180},
  "audit": {
    "compressed": [
      {"id": "frag_evt_07", "from": "full", "to": "focused", "reason": "budget", "sourceRefs": ["event:ev-007"]}
    ],
    "failures": []
  },
  "overflow": {
    "omitted": [
      {"id": "frag_style_example_03", "reason": "P3 overflow", "sourceRefs": ["setting:style"]}
    ]
  }
}
```

Spec 处理规则：

1. `audit.failures` 非空时必须中断写作流程。P0 或 P1_min 超限表示硬规则或章契约最小集无法安全进入 context，Spec 应建议拆章、缩小目标或请求 CLI 渲染更小 scope。
2. `compressed` 片段进入 prompt 时必须保留压缩级别。`focused` 或 `summary` 只能作为压缩事实使用，不得被当作完整历史或完整设定。
3. `omitted` 片段只能作为可补查引用。Spec 不得用自己的缓存、对话记忆或推测内容补全 omitted 片段。
4. repair 阶段可根据 verifier 失败项补调相关 CLI view。
5. 若预算使用接近上限，Spec 应在任务列表或提示中降低 P2/P3 的承担密度，优先保证 P0/P1 完整落地。

> Packet 输出结构见 `contracts/cli/json-schemas/chapter-context.schema.json`。`sourceRefs` 字符串格式见 `contracts/cli/entity-ids-sourcerefs.md`（SSOT）。

## 7. 诚实省略机制

`chapter context` 命令对无数据支撑的层**诚实省略**而非静默 stub：

- `chapter-contract` 层（章契约表未实现）→ `overflow.omitted`，reason=`no_data_backing_table`
- `character-snapshot` 层（角色快照表未实现）→ `overflow.omitted`，reason=`no_data_backing_table`
- `subplot-situation` 层（支线局面表未实现）→ `overflow.omitted`，reason=`no_data_backing_table`

这三个层是**规划态**（对应实体未实现），CLI 不用假数据填充，而是在 audit/overflow 中显式记录省略原因，让 Spec 知道这些上下文当前不可用、需通过其他方式获取或等待对应切片落地。
