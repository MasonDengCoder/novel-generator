# 契约治理：生成式契约源迁移

> **文档性质**：架构权衡说明（`CLAUDE.md` §11 归属 `docs/`）。
> **解决的问题**：Spec 开发需要精准契约，而当前 `contracts/cli/*.md` 手写契约不能保证准确，且已产生实证漂移。
> **与既有文档关系**：本文承接 `docs/cli-contract-alignment-audit-report.md`——那次治理用"删自抄表、替换为引用 SSOT"止住了表层漂移，但手写 SSOT 引用方式止不住根因漂移（见 §1.3 实证）。本文提出根因治理：**契约源从手写 md 迁到类型化代码**。
> **状态**：已实施，经契约治理 01–05 切片落地，并经 V2 错误协议批次 `contract-registry-v2-01~05` 推进到**完整契约生成 + V2 默认化**（`contracts/cli/*.md` 机器列/生成段与 `json-schemas/*.json`、`command-error-matrix.md`、`examples/INDEX.md`、`contract-tests/INDEX.md` 均为生成物；`commands.md` 行为语义段/退出码表由命令契约注册表 + `ErrorCatalog` 生成；`scripts/check-generated-drift.sh` 为六类受控产物的全量漂移门禁；默认错误协议为 V2，V1 转弃用兼容路径，见 §6.5）。本文不承载实现进度快照（见 `repository/dev-progress.md`）。

## 1. 问题：契约为什么不能保证准确

### 1.1 Spec 对契约的硬要求

Spec 运行层是 CLI 的机器消费方，不是人。它要凭契约做这些判断：

- 遇到退出码 21 要停止推进并走 repair 路径；
- 遇到错误码 `content_modified_externally` 要触发 hash 重算；
- 读 `chapter context --json` 要按 `fragments[].sourceRefs` 取稳定实体 ID，不能见 rowid 或 `.novel/` 路径。

这些判断要求契约**精准**——字段名、类型、退出码数值、错误码字符串、枚举取值都不能含糊。契约不准，Spec 写出来的流程逻辑就是错的。

### 1.2 当前契约层结构

```
contracts/cli/
├─ commands.md          (1800 行，46 命令，每个带参数表+退出码表+行为散文)
├─ exit-codes.md        (546 行，§A 生效码 + §各命令退出码表)
├─ error-codes.md       (150 行，§A 错误码 + 细分子表 + 命令场景复用表)
├─ json-output.md       (538 行，纯净性 + schemaVersion + 错误对象)
├─ views-scopes.md      (89 行，受控 view/scope 名)
├─ json-schemas/*.json  (27 份手写 JSON Schema，26 份声明 2020-12)
├─ examples/*.golden.json + .txt  (golden 样例)
├─ fixtures/*.sh        (测试世界 fixture)
└─ generated/*.gen.rs   (spec-gen 从 @codegen 生成的契约测试，仅 2 个 domain)
```

### 1.3 实证漂移：契约从未真正"先行"

项目宣称"契约先行"（`CLAUDE.md` §13），但手写 md 为源的契约**实际从未保证先行**，已产生可验证漂移：

| 漂移项 | 文档说法 | 代码实际 | 后果 |
|---|---|---|---|
| `external_modification` 退出码 | `error-codes.md` §A 声称 `5` | `ExitCode::ExternalModification = 5`，但细分码 `content_modified_externally` 经 `exit_code()` 映射到 `ContentModifiedExternally = 21` | Spec 不知信 5 还是 21 |
| 命令退出码表重复 | `commands.md` 每命令一表 + `exit-codes.md` 每命令一表，表顶挂"若与 SSOT 冲突以 SSOT 为准" | 92 张表手抄 | "以 SSOT 为准"这句话本身就是机制承认保证不了准确 |
| JSON Schema 与 struct | 27 份手写 schema | `renderers/*.rs` 的 `Serialize` struct | 无机制保证 schema 与 struct 一致 |
| Schema 是否被满足 | 27 份 schema | 契约测试仅手写字段存在性断言，无 schema 校验器 | **schema 从未被验证**，是文档摆设 |

`repository/decisions.md:31` 记录：项目已做过一次"删自抄退出码表、替换为引用 SSOT"治理。但**手写 SSOT 引用方式止不住漂移**——治标后 `external_modification` 漂移复现。根因是契约源是散文 md，靠人抄、靠人"以 SSOT 为准"对齐，机制上不可能保证准确。

### 1.4 spec-gen 现状：事后查漂移，非源头防漂移

项目已有 `crates/spec-gen`（dev-only xtask）：

```
现状链路：
  openspec/specs/**/spec.md 的 @codegen 块（人工）
    → spec-gen generate → contracts/cli/generated/*.gen.rs（契约测试）
    → check-generated-drift.sh 事后比对生成物与源
```

它做到三件事：构造性生成测试、SSOT 闸（`@codegen` 引用的 outcome 查不到 `exit-codes.md` 即 bail）、drift 门禁。但**只铺在 2 个 spec**（`chapter-context`、`chapter-lifecycle`），且本质是"事后发现漂移"——羊已经跑了才追。它没有把契约**源头**从散文迁到类型化代码。

## 2. 治理方向：契约源迁到类型化代码

### 2.1 核心判断

代码里已有三样**类型化、自洽、唯一权威**的东西，它们本就是契约源，只是还没被当契约源用：

```
契约源（已在代码里，待提升）          对应契约产物
─────────────────────────────────    ─────────────────────────
renderers/*.rs 的 Serialize struct  → json-schemas/*.json（结构契约）
errors/mod.rs 的 enum + exit_code() → exit-codes.md / error-codes.md（错误契约）
commands/*.rs 的 clap 命令树          → commands.md 命令语法段（命令契约）
openspec/specs/**/spec.md scenario  → *.md 行为语义段（语义契约，保留手写）
```

治理不是新造契约源，是**把已有的类型化代码显式提升为契约源，让生成器从它们渲染 `contracts/cli/*.md`**。手写 md 从"源"降级为"生成物"。

### 2.2 与"纯 C 实现+"的区别

本方案不是"实现即契约"（CLI 运行时 emit 契约），而是"类型化代码先行 + 生成契约"：

| 维度 | 纯 C（实现即契约） | 本方案（三源生成） | 旧手写 md |
|---|---|---|---|
| 结构契约准确度 | ✓ 实现=契约 | ✓ struct=契约 | ✗ 手抄漂移 |
| 契约先行（Spec 可提前消费） | ✗ 得等实现 | ✓ struct 骨架可先冻结 | ✓ md 先写 |
| 语义契约准确度 | 靠 doc 注解 | 靠 spec scenario | ✗ 手抄漂移 |
| 语义契约先行 | ✗ | ✓ spec 保留 | ✓ |
| 漂移可机器检测 | ✓ | ✓ 源 vs 生成物 diff | ✗ |
| 规划态实体覆盖 | ✗（无实现可 emit） | ✓（spec 保留） | ✓ |

本方案是表中唯一四维皆可的形态。它保住"契约先行"（struct 骨架/enum 变体先于实现冻结，Spec 可提前消费），同时用生成器保住"契约与代码一致"（生成物与源 diff 即红）。

### 2.3 时序：struct 先行如何成立

"契约先行"在本方案下的真实含义，是 **struct/enum 变体先于实现冻结**：

```
1. 写 struct 骨架（字段名/类型/doc，未接 service，字段已冻结）
2. 生成 *.md / *.schema.json 契约
3. Spec 可消费契约（即使实现还没写完）
4. service 填实现，renderer 把 struct 接上数据
5. 生成器从 struct 重新生成契约 → 与步骤 2 冻结的契约 diff → 漂移即红
```

struct 骨架先行 = 契约先行。实现后填，生成器保证填的过程中契约字段没漂移。这与现在"先写 spec `@codegen` 块再实现"是同一时序，只是契约源从散文 md 挪到 struct/enum。

## 3. 技术选型：三源生成 + 依赖

### 3.1 依赖选型（已定）

| 用途 | 依赖 | 版本 | 作用 | 消除的漂移 |
|---|---|---|---|---|
| struct → JSON Schema | `schemars` | 0.8 | 从 `Serialize` struct 编译期导出 JSON Schema（Draft 7） | `json-schemas/*.json` 手写 |
| enum → 错误码/退出码表 | `strum` | 0.26 | `EnumIter` 遍历变体 + `serialize` 替代手写 `as_str()` match | `error-codes.md`/`exit-codes.md` 手表 + `as_str()` 手写 match |
| clap 树 → 命令语法 | `clap 4` 自带 API | — | 遍历 `Command::get_args()`/`get_subcommands()` | `commands.md` 命令语法段 |

**两条新依赖**（`schemars` + `strum`），均为 Rust 生态主流包，与现有 `edition 2021` / `clap 4` / `serde` 同源生态，无冲突。

### 3.2 schemars 0.8 的版本后果（已定，需统一）

`schemars 0.8` 生成 **Draft 7**。现有 27 份手写 schema 中 26 份声明 `2020-12`、1 份已声明 `draft-07`。生成器介入后，输出 draft 版本由生成器决定，须统一：

- 将 26 份手写 schema 的 `$schema` 统一改为 `draft-07`（或待其被生成物覆盖时自然统一）。
- 契约测试未 pin `$schema` 字段（已核实：`contract_*_schema.rs` 仅手写字段存在性断言，无 schema 校验器），迁移不红测试。

### 3.3 可选增强：schema 校验闭合"运行时准确"

仅"源头生成"保证结构与代码一致，但不保证**生成的 schema 被命令真实输出满足**。现有 schema 从未被校验过（§1.3）。建议纳入 `jsonschema` crate（Draft 7 校验器）作可选增强：

```
json-schemas/*.json（生成）
  → jsonschema crate 校验命令真实 --json 输出
  → 第一次让 schema 成为被强制的活契约，而非摆设
```

源头生成（结构准）+ 运行时校验（输出准）= 双重保证，正面闭合"契约准确性"。

## 4. spec-gen 职责扩张

`spec-gen` 从"正则解析 md 生成测试"转向"读三源结构化数据 + spec 语义生成 `contracts/cli/*.md`"：

```
输入源：
  ├─ renderers/*.rs 的 Serialize+JsonSchema struct   （结构契约，schemars 导出）
  ├─ errors/mod.rs 的 EnumIter+strum enum             （错误契约，strum 遍历）
  ├─ commands/*.rs 的 clap 命令树                      （命令语法，clap API）
  └─ openspec/specs/**/spec.md 的 scenario             （语义契约，保留手写）

输出：
  ├─ contracts/cli/commands.md     （命令语法段生成 + 行为语义引用 spec）
  ├─ contracts/cli/exit-codes.md   （从 enum 生成，零漂移）
  ├─ contracts/cli/error-codes.md  （从 enum 生成，零漂移）
  ├─ contracts/cli/json-schemas/*.json（从 struct 生成，零漂移）
  ├─ contracts/cli/generated/*.gen.rs（现有，从 @codegen 生成测试）
  └─ contracts/cli/examples/*.golden.json（可选，从 struct+fixture 跑出生成）
```

`ssot.rs` 现有正则解析 `exit-codes.md`/`error-codes.md` 的逻辑逐步退役——数据源从散文 md 换成 `strum::EnumIter` 迭代器，不再靠正则猜表格。

## 5. 落地节奏：先解决准确性

项目开发不可能一蹴而就。本治理**先解决准确性**（最痛问题），设计合理性（Spec 反馈 CLI 形态是否合理）留后续迭代闭环：

```
阶段 0（前置）：修 SSOT 污染
  解决 external_modification 5 vs 21 矛盾——以 errors/mod.rs exit_code() 为准改文档
  （这是 Spec 能否启动的前置条件，漂移现在就在这个矛盾上）

阶段 1：接入三源生成
  schemars derive 加到 renderers/*.rs struct → 生成 json-schemas
  strum derive 加到 errors/mod.rs enum → 生成 exit-codes.md/error-codes.md
  clap API 遍历 → 生成 commands.md 命令语法段

阶段 2（可选）：schema 运行时校验
  jsonschema crate 校验命令输出 vs 生成 schema

阶段 3：spec-gen 职责切换
  ssot.rs 正则退役，改为读三源结构化数据
  check-generated-drift.sh 扩展为生成物全量漂移门禁

阶段 4：开发流程调整（文档化，非本治理强约束）
  功能定义（只要求不内容）→ 功能分析 → CLI 实现 → 生成契约 → Spec 开发
```

### 5.1 设计合理性的后续迭代

Spec 放最后开发有隐藏成本：CLI 形态在实现时无 Spec 侧反馈。例如 `chapter context --view` 的 `writer/verifier/repair` 三分是 CLI 侧先拍板，Spec 用起来若发现该五分，CLI + 契约 + Spec 全线返工。

三源生成保证**契约与代码一致**，但不保证**契约本身设计合理**。本治理的判据是准确性优先：先用三源方案解决最痛的准确性问题，后续 Spec 开发若暴露设计不合理，则**继续迭代 CLI + 契约**——这恰是三源方案的优势：改 CLI 代码 → 契约自动重新生成，返工成本被生成器压到最低，不像手写 md 时代改一处忘三处。

## 6. 影响面与边界

### 6.1 会动的稳定契约

- `exit-codes.md` / `error-codes.md`：从手写降为生成物。`external_modification` 退出码以代码为准（5 vs 21 矛盾消除）。
- `json-schemas/*.json`：从手写降为生成物，`$schema` 统一 draft-07。
- `commands.md`：命令语法段/参数表/行为语义段/退出码表降为生成物（语法由 clap 命令树生成，行为语义与退出码表由命令契约注册表 + `ErrorCatalog` 生成）。
- `command-error-matrix.md`、`examples/INDEX.md`、`contract-tests/INDEX.md`：新增受控生成物（命令错误矩阵 / 示例与 fixture 索引 / 契约测试索引，由注册表 + 文件系统清单驱动）。

这些是 `CLAUDE.md` §9 列的"稳定契约"。本治理改变它们的**维护方式**（手写→生成），不改变**契约语义**（退出码数值、错误码字符串、JSON 字段含义不变）。生成物与现状的 diff 即现状漂移的修复清单。

### 6.2 不动的边界

- SQLite schema、`.novel/` 内部路径、Rust module 名称仍是"非稳定实现细节"（`CLAUDE.md` §9），不进契约源。
- 语义契约继续留在 `openspec/specs/**/spec.md`，不被代码生成覆盖。
- 规划态实体（`repository/dev-progress.md` §7.2）无 enum/struct 可生成，继续走 spec 语义登记，不进生成器。

### 6.3 与 `CLAUDE.md` §13 的关系

`CLAUDE.md` §13 现要求"新增 CLI 功能时优先补契约（md）……再实现内部存储细节"。本治理后，"优先补契约"的落地形态从"先写 md 契约"改为"先加 struct/enum 变体 + derive 注解 + `@codegen` 块再实现"——先行的是类型化骨架，不是 md。md 变生成物。此措辞调整需随本治理同步更新 `CLAUDE.md` §13 与切片归档门禁。

## 6.5 V2 默认化与 CI 门禁（contract-registry-v2-05）

`contract-registry-v2` 批次把错误协议从 V1 迁到 V2（类型化错误目录 `ErrorCatalog` + 版本化错误信封）。治理收口切片 `contract-registry-v2-05` 完成默认化与门禁固化：

**默认化语义**：CLI 的默认错误协议为 V2——`ErrorProtocolVersion::default()` 为 V2，`--json` 失败输出为 `V2ErrorEnvelope`（`errorId`/`category`/`exitCode`/`message`，可选 `details`），进程退出码与信封 `exitCode` 均由错误类别派生（`ErrorCatalog` 类别 → 固定类别码）。V1 `ErrorObject` 转为**弃用兼容路径**：仅在调用路径显式选择 V1 时输出，逐字保持 V1 回归基线。V1 的物理移除由独立变更执行，须满足 `contract-v2-governance` 定义的三条件齐备准则，不在默认化切片内进行。

**CI 门禁**（`.github/workflows/ci.yml`，只调用仓库内可本地复跑命令，不在 CI 内联第二套校验逻辑）：

| 门禁 | 本地可复跑命令 | 预期退出码 |
|---|---|---|
| 生成物漂移（含手写生成物 `@generated` 标记完整性） | `./scripts/check-generated-drift.sh` | 正常 0 / 漂移 1 |
| 绕过契约注册表（clap↔注册表↔`ErrorCatalog` 交叉一致性、未登记错误 ID） | `cargo run -p spec-gen -- check`（同上脚本内部） | 正常 0 / 不一致 1 |
| 全量测试 | `cargo test -p novel-cli` | 全通过 0 / 失败非 0 |

门禁覆盖的受管产物（命令文档生成段、命令错误矩阵、示例/契约测试索引、`json-schemas/`、`exit-codes.md`/`error-codes.md` 机器列）以 `@generated` 标记界定生成边界；标记内手改或破坏标记即漂移红。三类受控产物由注册表 + `ErrorCatalog` + clap 树派生，退出码/错误码语义引用 SSOT，不在文档中重复定义表。

## 7. 待决项

1. **spec-gen 读源方式**：schemars/strum 导出的结构化数据，spec-gen 是直接调 `schemars::schema_for!()` / `strum::EnumIter::iter()`（需 spec-gen 依赖 novel-cli 的类型，或抽契约声明 crate），还是读生成好的中间产物（schema json / 错误码 json）。前者类型安全但耦合，后者解耦但多一步中间产物。落地 change 时定。
2. **行为语义散文归属**：`commands.md` 的行为语义段（参数说明、行为描述）由 `contract-registry-v2-04` 落地为“注册表驱动生成”：行为语义主干（`summary`/`inputs`/`outputs`/`guard`）来自 `CommandContract` 注册表，`@generated` 标记外的补充说明（如 `init` 目录结构长叙述）保留手写豁免段。待决项已收敛，不再未决。
3. **golden 样例是否生成**：现 golden 手写。可选从 struct + fixture 跑命令生成，但 golden 的"期望值"语义需保留人工断言（哪些字段必须出现），全量生成会丢失断言意图。

## 8. 结论

本治理把契约源从手写散文 md 迁到类型化代码（struct/enum/clap 树），用 `schemars 0.8` + `strum` + `clap 4` 三源生成 `contracts/cli/*.md`，可选 `jsonschema` crate 闭合运行时校验。它保住契约先行（struct 骨架先冻结），根因消除漂移（生成物与源 diff 即红），先解决最痛的准确性问题，设计合理性留后续迭代。`external_modification` 5 vs 21 矛盾作为前置先行修复。

下一步：走 OpenSpec change 把本治理落成可推进的切片任务。
