## 一、项目概况

`novel-generator` 是运行在 Claude Code 上的托管式小说创作工具包。用户只做大势规划（灵感 → 四极 → 主线 → 旁门），后续逐章撰写全程 LLM 托管，以《创作即创世》方法论为内核。

### 2.2 关键架构决策

- **软硬分层 + 严格单向依赖**：软层（LLM harness）→ 硬层（Python 状态机），硬层零感知、可脱离 LLM 独立运行与测试。这是全系统最重要的可测性保证。
- **唯一真相源**：单一 SQLite `index/novel.db`，正文绝不入库（仅弱引用 + 字数遥测），Bible 是 DB 派生视图。
- **不可越级修正**：四层轮回权限递增，越级处置由 CLI 权限边界钢性拦截，不靠 LLM 自觉。
- **核心判断**：LLM 记忆不可靠，凡长程必须记住的东西全部下沉成确定性 DB 数据兜底。
- **原语分配判据**：跨阶段不变式→Rules、确定性机械动作→Hook、阶段性多步流程→Skill、读完即弃的监测→Subagent。能下沉到 Hook 的绝不写进 Rules。

## 三、经验教训

| 经验 | 说明 |
|------|------|
| **设计先行、文档即蓝图** | 坚持纯文档项目阶段把设计冻结，编码以文档为蓝图而非反推，降低返工风险。 |
| **设计抉择显式化（DD-1~9）** | 把关键取舍单列编号记录，避免后人"知其然不知其所以然"，也便于基线变更追溯。 |
| **Why/How 分离** | 详细设计只写 How、设计理念只写 Why，两文档各司其职，避免实现细节与判断依据混杂难维护。 |
| **基线变更需留痕** | M2 后两次基线变更（2026-06-09 O-缺口、2026-06-10 O1~O7）均在 TODO 里程碑留痕，保持可追溯。 |
| **文档卫生** | 文档被升格/合并/取代后删除过期原件（如优化方案.md 退役删除），删除前 grep 改向，不留死链。 |
| **测试边界要早定** | NFR-5 明确确定性网只覆盖可判定行为、不覆盖 LLM 判定质量，避免后期陷入"测不了文笔"的困境。 |

## 五、后续演进建议

1. **进入编码阶段**：以详细设计为直接依据实现硬层（`core/db.py`、5 分片 schema、CLI 子命令、`element_manager`），优先打通 `test_layer1~5` 守护网。
2. **回填测试结果**：编码后回填测试文档六~八章（覆盖率/缺陷/遗留），完成 M3 真正准出。
3. **字段冻结推进**：当前字段未冻结，按"某表跑通即纳入冻结"逐步收紧，承重字段优先由 `test_load_bearing_fields.py` 守护。
4. **方法论版本化**：openspec 作为最慢变层独立维护，理念演进时同步版本化 spec。
5. **软层半自动验证**：为 skill 多步流程建立 CLI 调用序列断言，弥补 LLM 流程不可全自动化测试的缺口。
6. **回填实现侧总结**：编码完成后，本报告补充实现工作量、实测数据、与设计的偏差分析。
