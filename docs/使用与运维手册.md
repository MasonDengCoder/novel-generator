# 使用与运维手册 · novel-generator

> 本文档合并瀑布模式下的「用户手册」与「操作（运维）手册」，为小型项目精简版。
> 上半·用户侧（一~四章）面向创作者：装好、按流程用、单次 1–2 章续接。
> 下半·运维侧（五~七章）面向维护者：DB 备份、schema 冻结约束、hook 降级、无 LLM 环境驱动。

# 上半 · 用户手册

## 一、这是什么

`novel-generator` 是运行在 Claude Code 上的**托管式小说创作工具包**。你只做大势规划（灵感 → 四极 → 主线 → 旁门），后续逐章撰写全程由 LLM 托管。以《创作即创世》方法论为内核。

核心分工：
- **你**：定灵感奇点、世界四极（硬边界）、主线定数、旁门元素。
- **工具**：管 context、生成 prompt、维护生命周期状态、守护创作元素，逐章写。

## 二、安装

### 2.1 前置依赖

- 宿主机须有 **python3 ≥ 3.8**（硬层零第三方依赖，仅标准库）。
- 软层创作需在 **Claude Code** 环境中运行。

### 2.2 完整安装（软层 + 硬层）

```bash
node packages/novel-spec/install-spec.js [目标目录]
```

安装软层时自动拉取硬层（FR-2.1 一键安装）。安装幂等，重复执行不破坏既有文件。

### 2.3 仅装硬层（无 LLM 环境）

```bash
node packages/novel-lifecycle-cli/install-cli.js [目标目录]
```

供无 LLM 环境单独驱动确定性状态机（FR-2.2）。

### 2.4 验证安装

```bash
scripts/novel-cli init      # 初始化项目，建空库 index/novel.db
```

`scripts/novel-cli` 带 shebang + chmod 755，**无需 `python3` 前缀**直接执行。

## 三、创作流程怎么用

四层嵌套轮回，从大势到逐章。每一步都由对应 skill 托管，你只在关键决策点参与。

### 3.1 奠基阶段（定大势，你深度参与）

| 步骤 | 你做什么 | 工具落点 |
|------|---------|---------|
| 捕捉灵感 | 给出灵感奇点 | `capture-inspiration` → `stage complete inspiration` |
| 立前提 | 确认一句话前提 | `draft-premise` |
| 定四极 | 划世界硬边界（力量上限/道德底线等） | `design-world-boundary` → `stage complete world-boundary` |
| 定风格 | 设叙事声音 + 敏感词 | `design-style-guard` |
| 定主线 | 标注不可变主线定数 | `design-mainplot` → `stage complete main-plot` |
| 布旁门 | 加支线/伏笔/爽点/承诺 | `design-destiny` → `db add-*` |

### 3.2 编织阶段（分批推进，非一次全生成）

```
weave volume → event → section → chapter
```

由 `weave-fate` 托管，滚动窗口分批细化（卷 → 事件 → 节 → 章），不要求首次全生成（FR-5.2）。

### 3.3 写作阶段（单次 1–2 章，自动续接）

每章由 `write-prose` 托管，走章内四相：

```
prose start  →  prose phase（逐相推进）  →  prose end
```

- `prose end` 通过章必达 must 裁决后，章 `status=done`。
- 残余由 `extract-residue` → `prose residue` 落库，供续接参考。

### 3.4 封档阶段

```
finalize check  →  finalize dispose  →  finalize seal
```

由 `seal-creation` 托管，过孤儿检测与世界圣经校验后封档，DB 进入只读。

## 四、单次 1–2 章如何续接

工具为"忘了就崩的长程记忆"做了 DB 兜底，因此跨会话续接安全：

1. 新会话直接对下一章发起 `write-prose`，工具自动读 DB 恢复上下文。
2. `pre-write-chapter.sh` hook 自动注入本章 threads（线索绑定）+ 到期预警。
3. 上一章的 `chapter_residue` 残余作为续接钩子被读取。
4. 你无需手动复述前情——长程状态都在 `index/novel.db`，不依赖 LLM 记忆。

> 这是核心设计：LLM 记忆不可靠，凡长程必须记住的东西全部下沉成确定性 DB 数据兜底。

# 下半 · 运维手册

## 五、数据源维护

### 5.1 novel.db 位置与地位

- 单一 SQLite 库：`index/novel.db`，是**唯一真相源**。
- 唯一访问点 `core/db.py`，所有读写经 `scripts/novel-cli` 子命令分发，软层任何阶段不得绕过 CLI 直接读写（铁律 1）。
- 正文**绝不入库**：DB 只存 `prose_ref`（弱路径引用）+ `word_count` 遥测（DR-2）。正文本体在工作目录的 `c<M>.md` 等文件中。

### 5.2 备份

由于 DB 是唯一真相源，备份策略最简：

```bash
cp index/novel.db index/novel.db.bak-$(date +%Y%m%d)   # 冷备：拷整库文件即可
```

- 备份时机：每卷封档（`cycle close-volume`）后、整体 `finalize seal` 前。
- 正文文件（`c<M>.md`）须与 DB 一并备份——DB 只存弱引用，丢了正文文件无法从库恢复。
- 恢复：用 DB 备份 + 对应正文文件成对回滚，避免 `prose_ref` 指向缺失文件。

### 5.3 封档后只读

`finalize seal` 后 DB 进入只读（DC-4），`core/db.py` 拦截任何写操作。如需续写已封档项目，属设计外操作，须人工评估，不在常规运维范围。

## 六、schema 冻结维护约束

| 约束 | 运维含义 |
|------|---------|
| 仅 `CREATE TABLE IF NOT EXISTS` | 运行期冻结后**永不 ALTER/DROP**，补字段一律靠新建表（DR-5/DC-2） |
| 5 分片增量叠加 | layer1~5 顺序叠加，跨 layer 外键仅向低编号引用（DC-5） |
| 守护测试 | 改动 schema 必须先过 `test_layer1~5` + `test_load_bearing_fields.py` |
| 当前初始阶段 | 字段未冻结，按需增删；某表结构稳定后再纳入冻结，纳入即不可逆 |

> 维护红线：一旦某分片冻结，绝不就地改字段。任何"加字段"的需求都转化为"建新表"，由守护测试把关。

## 七、容错与降级运维

### 7.1 hook 失败静默降级

所有 hook 异常时静默降级（`exit 0`），**绝不阻断写作**（NFR-4 / 铁律 6）。运维须理解两类语义：

| 类型 | 行为 | 运维判断 |
|------|------|---------|
| 业务阻断 | 敏感词命中、非白名单写库 → 真阻断 | 符合预期，按提示修正 |
| 脚本自身异常 | DB 不可读、依赖缺失 → `exit 0` 放行 | 写作不受影响，但需排查环境，否则保护静默失效 |

> 风险提示：脚本异常降级意味着 `guard-db-write.sh` 等保护可能"静默失效"。运维应定期确认 hook 脚本本身可正常执行（如手动跑一次、检查 python3 可用），避免保护长期空转而无人察觉。

### 7.2 无 LLM 环境单驱动硬层

硬层对软层零感知，可脱离 LLM 独立运行（NFR-3）：

- 仅装硬层（§2.3）后，可直接用 `scripts/novel-cli <子命令>` 驱动状态机、查 DB 状态、跑测试。
- 适用场景：CI 回归、状态核对、数据修复脚本、离线审计。
- 此模式下软层 skill/agent/hook 全部不参与，只有确定性状态机运转。

### 7.3 常见运维动作速查

```bash
scripts/novel-cli bible full          # 渲染完整世界圣经（DB 派生视图，无独立存储）
scripts/novel-cli context chapter <M> # 查某章线索绑定
scripts/novel-cli finalize check      # 跑终检（孤儿/主线覆盖性校验），不改状态
```

> Bible 是 DB 的派生渲染（`bible core|active|dormant|full`），无独立存储（FR-3.3/DR-3），无需单独备份。
