# 用户指南：章节管理

本指南说明如何使用 `novel chapter` 命令管理小说章节，以及如何处理外部修改检测错误。

## 快速开始

### 创建和管理章节

```bash
# 1. 初始化项目（如果还没有）
novel init "我的小说项目"

# 2. 创建新章节
novel chapter create "第一章：序幕"
# 输出: ✓ 章节创建成功
#       ID: chapter-001
#       标题: 第一章：序幕

# 2a. （可选）创建章节时归属到卷，使封卷/导出/卷末报告包含本章
novel volume create "第一卷" --order 1            # 先建卷（卷 ID 自增）
novel chapter create "第一章：序幕" --volume 1 --json   # volumeId 写入 chapters 表

# 3. 准备正文内容
cat > chapter1.md << 'EOF'
# 第一章：序幕

这是章节的正文内容。可以使用 Markdown 格式编写。

## 场景一

人物对话和描述...
EOF

# 4. 更新章节正文
novel chapter update chapter-001 --content chapter1.md
# 输出: ✓ 章节正文更新成功

# 5. 查看章节
novel chapter get chapter-001

# 6. 列出所有章节
novel chapter list
```

### JSON 输出（供程序消费）

```bash
# 获取 JSON 格式输出
novel chapter get chapter-001 --json
novel chapter list --json

# 示例输出
{
  "schemaVersion": "3",
  "id": "chapter-001",
  "title": "第一章：序幕",
  "content": "# 第一章：序幕\n\n...",
  "wordCount": 150,
  "createdAt": "2026-06-29T10:00:00Z",
  "updatedAt": "2026-06-29T10:05:00Z"
}
```

## 外部修改检测与处理

### 为什么需要外部修改检测？

`novel` CLI 使用 SHA-256 hash 来保证章节正文的完整性。当你：

1. 通过 `novel chapter update` 写入正文时，CLI 会计算并存储正文的 hash
2. 读取章节时，CLI 会重新计算 hash 并与存储的值比对
3. 如果 hash 不匹配，说明文件被外部工具修改过（绕过了 CLI）

**为什么要阻止外部修改？**

- 保证世界状态的一致性（SQLite 元数据可能与实际正文不同步）
- 防止意外覆盖（多人协作或自动化工具可能引起冲突）
- 明确修改来源（所有修改都应该通过 CLI 记录）

### 场景 1：直接编辑正文文件

**问题**: 你使用文本编辑器直接修改了 `.novel/content/chapters/chapter-001.md`。

```bash
# 手动编辑文件
vi .novel/content/chapters/chapter-001.md

# 尝试读取章节
novel chapter get chapter-001
```

**错误输出**:
```
❌ [content_modified_externally] 章节 chapter-001 的正文已被外部修改，
请运行 `novel chapter reimport chapter-001` 重新导入。
（退出码 21）
```

**解决方案**:

如果你**确认**这次外部修改是有意的且正确的，使用 `reimport` 命令重新导入：

```bash
# 重新导入章节，更新 hash 和元数据
novel chapter reimport chapter-001
# 输出: ✓ 章节重新导入成功

# 现在可以正常读取
novel chapter get chapter-001
```

**`reimport` 做了什么？**

1. 读取当前正文文件内容
2. 重新计算 SHA-256 hash
3. 重新统计字数
4. 更新 SQLite 中的元数据（hash, word_count, updated_at）

### 场景 2：批量验证正文完整性

**用途**: 检查所有章节是否被外部修改。

```bash
# 验证所有章节的 hash
novel chapter list --verify-hash
```

**如果有章节被修改**:
```
❌ [content_modified_externally] 检测到外部修改：
  - chapter-001
  - chapter-003
请逐个运行 `novel chapter reimport <id>` 重新导入。
（退出码 21）
```

**批量修复**:
```bash
# 方法 1：手动逐个修复
novel chapter reimport chapter-001
novel chapter reimport chapter-003

# 方法 2：使用脚本批量修复（谨慎使用）
novel chapter list --json | jq -r '.chapters[].id' | \
  xargs -I {} novel chapter reimport {}
```

### 场景 3：版本控制恢复导致的不一致

**问题**: 你使用 `git checkout` 或 `git reset` 恢复了旧版本的正文文件，但 SQLite 数据库没有一起回退。

**症状**:
- 正文内容是旧版本
- SQLite 中的 hash 是新版本
- 读取时出现 hash mismatch 错误

**解决方案**:

```bash
# 选项 1：重新导入正文（接受文件系统的版本）
novel chapter reimport chapter-001

# 选项 2：重新写入正文（接受数据库的版本）
novel chapter update chapter-001 --content /path/to/correct/version.md
```

**建议**: 在使用版本控制时，`.novel/` 整个目录应该一起管理（包括 `novel.db` 和 `content/`）。

### 场景 4：多人协作中的冲突

**问题**: 两个人同时修改了同一章节的正文文件。

**预防措施**:

1. **使用版本控制**: 让 Git 处理文件冲突
2. **通过 CLI 更新**: 始终使用 `novel chapter update` 而不是直接编辑
3. **项目级写锁**: CLI 会自动使用 `.novel/.write.lock` 防止并发写入

**如果已经冲突**:

```bash
# 1. 解决 Git 冲突，确定最终版本
git merge <branch>
# 手动解决冲突，保存最终版本

# 2. 重新导入章节
novel chapter reimport chapter-001

# 3. 提交最终版本
git add .novel/content/chapters/chapter-001.md .novel/novel.db
git commit -m "Resolve chapter-001 conflict"
```

## 最佳实践

### DO ✅

- **始终通过 CLI 更新正文**: `novel chapter update chapter-001 --content file.md`
- **定期验证完整性**: `novel chapter list --verify-hash`
- **版本控制整个 `.novel/` 目录**: 包括 `novel.db` 和 `content/`
- **使用 `reimport` 接受外部修改**: 当你确认修改是正确的

### DON'T ❌

- **不要直接编辑 `.novel/content/chapters/` 下的文件**: 会导致 hash mismatch
- **不要绕过 CLI 修改 SQLite**: 会破坏一致性
- **不要忽略 hash mismatch 错误**: 说明数据不一致
- **不要删除 `.novel/tmp/` 中正在使用的临时文件**: CLI 会自动清理

## 常见问题

### Q: 为什么不能直接编辑正文文件？

A: 直接编辑会导致 SQLite 中的 hash 和实际文件内容不一致。CLI 通过 hash 检测这种不一致，保护世界状态的完整性。如果你需要使用外部编辑器，编辑后运行 `reimport` 重新导入。

### Q: `reimport` 会丢失数据吗？

A: 不会。`reimport` 只更新 hash 和 word_count，不修改正文内容。它是"接受外部修改"的安全方式。

### Q: 如何备份章节？

A: 备份整个 `.novel/` 目录即可，包括：
- `novel.db`（元数据）
- `content/chapters/`（正文文件）

或者使用版本控制（Git）管理整个项目。

### Q: 可以用 Markdown 编辑器实时预览吗？

A: 可以查看，但不要保存修改。推荐工作流：
1. 在外部编辑器中编辑 `draft.md`
2. 满意后运行 `novel chapter update chapter-001 --content draft.md`
3. CLI 会自动计算 hash 并更新元数据

### Q: 字数统计包括 Markdown 标记吗？

A: 不包括。CLI 会去除 Markdown 标记后统计纯文本字数，中文按字符计数。

### Q: 退出码 21 是什么意思？

A: 退出码 21 表示 `E_CONTENT_MODIFIED_EXTERNALLY`，即检测到正文被外部修改。这是一个硬阻断错误，必须运行 `reimport` 后才能继续操作。

## 技术细节

### 存储结构

```text
.novel/
  novel.db                      # SQLite 数据库
    chapters 表:
      id: chapter-001
      title: 第一章
      content_path: content/chapters/chapter-001.md
      content_hash: sha256(正文内容)
      word_count: 150
      created_at: 2026-06-29T10:00:00Z
      updated_at: 2026-06-29T10:05:00Z
  
  content/
    chapters/
      chapter-001.md            # 实际正文文件
  
  tmp/                          # 临时文件（写入时使用）
  .write.lock                   # 项目级写锁
```

### Hash 计算

- 算法: SHA-256
- 输入: 正文文件完整内容（UTF-8）
- 存储: SQLite `chapters.content_hash` 字段
- 验证时机: 每次 `get` 和 `list --verify-hash`

### 原子写入流程

```
1. 获取项目级写锁 (.write.lock)
2. 开启 SQLite transaction
3. 验证章节存在且状态允许修改
4. 读取输入正文文件
5. 写入临时文件 (.novel/tmp/<uuid>.md)
6. 计算 hash 和 word_count
7. 更新 SQLite 元数据
8. 原子替换正式文件 (rename)
9. 提交 SQLite transaction
10. 释放写锁
```

这个流程保证了 SQLite 和文件系统的事务一致性。
